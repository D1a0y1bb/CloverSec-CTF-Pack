# 批量交付

一次要处理 5 道以上，或用户直接给一个文件夹时读这份。单题交付不用读。

批量交付出问题的地方通常不在题目本身，而在分工：题目做了一半没人收尾、两个写入者互相覆盖、主 Agent 把上下文耗在轮询上、最后没有人做对账。

默认做法：不追求并行，按题目类型分批做；自己做得完的就自己做，不要开一堆子 Agent。

## 1 先分批，再开工

**一批 3 到 5 道。做完一批，逐题核对，再开下一批。** 不要一次把 20 道题全铺开。

分批的方式按题目类型或按材料来源切，不要按"随机 5 道"切——同一批的题往往共享基础镜像、依赖和踩坑经验，放一起做能省时间。

开工前把批次写下来，交给用户看一眼：

```text
批次 1（单服务容器题 4 道）：Web-a、Web-b、Web-c、Web-d
批次 2（多服务题 3 道）：Web-e、Web-f、Web-g
```

**题目少于 5 道时自己做，不要开子 Agent。** 开出来的协调成本比省下的时间多。

## 2 一个目录一个写入者

**同一个交付目录，同一时刻只允许一个写入者。** 这是硬规则。

并行写同一个目录的后果不是"慢一点"，是交错覆盖：A 写了 Dockerfile、B 又按自己的方案覆盖回去，两边都以为自己的版本生效了。这类问题在交付时才暴露，排查成本极高。

- 分工按**目录**切，不按文件类型切。
- 派活时把范围写死：`你只负责 <题目目录>，不要碰其他目录`。
- 主 Agent 自己也要守规矩：派给子 Agent 的目录，自己不要再去改。

### 停不下来的时候不要派第二个

子 Agent 联系不上、发消息没有回音，**不等于它死了**。

- 它可能正在读材料（翻大目录、解 rootfs tar 都要很久），这段时间不会写任何文件。
- 判断"在不在干活"用轮次和工具调用，不要只看文件 mtime。**mtime 旧只能说明"没写文件"，不能说明"死了"。**
- 联系不上时，正确动作是**停下来问用户**，或者等这一批跑完再做下一批。不要因为"看起来卡住了"就派一个新 Agent 接手同一个目录。

接手任务书里禁止写"前一个 agent 已经死掉了"。写这句话之后，一旦原 Agent 还活着，这个目录就有两个写入者了。

已经有两个写入者时，处理办法是**等两边都停下来，做逐题对账**：以"服务层完整、漏洞链不变、白名单干净"为标准重新检查产物，谁写的不管，符合标准才算完成。对账要读目录现状和文件时间戳，不要相信任何一方的叙述。

### 验证也要排队

`verify.sh` 的镜像 tag 是按题目目录路径算的（`ctf-verify-<目录名>-<校验和>`）。两个人同时对同一个目录跑验证，会互相 `build` / `rmi` 同一个 tag，结果不可信。

**一个目录同一时间只跑一个 verify。**

**一台机器也不要并发跑多道。** 真实事故：43 道题并发验证，其中一道跑了 1846 秒判 `failed`，单独重跑却 `passed`——根因是并发抢核，不是题目问题，但已经触发了一轮全量重跑，用户等了几个小时。

- 验证串行跑，或者最多同时 2 道。
- 并发跑出来的 `failed`，**先单独重跑一次再当作结论**。
- 用户催速度时，正确的做法是减少题量或拆分批次，不是加并发。

### 单题止损线

一道题卡住时，**不要死磕到用户来问**。

- 同一道题的 `solve.py` 调试超过 **10 轮**或 **1 小时**，停下来报告：卡在哪、试过什么、需要用户决定什么。
- 用户明确说过「你看看官方解，如果实在这个题目写不了一键 solve，只要官方解说能解出、题目环境没问题，那就是 ok 的」。**官方解在本环境不可复现时，标 `incomplete` 是合法交付**，不是失败。
- 为了打通 `solve.py` 去改题目链路，是降级，不许做。

## 3 子 Agent 任务书

每道题（或每批题）给一份任务书。任务书写全，子 Agent 就不用回头问，也不用把长文本塞进每个 prompt。

```markdown
# 任务：<交付目录名>

## 材料
- 原始材料：<绝对路径>
- 已有交付目录：<绝对路径，没有就写"无">
- 参考文档：<Skill 的 references/xxx.md>

## 交付位置
<绝对路径>/容器题/<交付目录名>/
你只负责这一个目录，不要碰其他目录。

## 难度基线（开工前先核对，不一致就停下报告）
- 漏洞类型：<...>
- 链路：<... 步>
- 服务拓扑：<nginx + php-fpm + MariaDB>
- 运行时版本：<PHP 5.6>
- 与原材料的差异：<无 / 列出被替换的部分>

## 手册判断部分的来源
- 出题人材料：<路径，例如 官方题解 README.md>
- 外部 writeup：<路径，只能当线索，写入前必须实测核对>
- 都没有：在该节写 TODO(人工填写)，并在回报里点名

## 验证方式
<本机 / 远程 amd64 的完整命令>

## 回报格式
<见第 4 节>
```

任务书里要写清的三件事，缺一个就会出问题：**交付到哪、不许碰哪、判断部分的来源在哪**。

## 4 回报格式

子 Agent 干完必须按这个格式回报，缺项就是没做完：

```text
<交付目录名>: passed | partial | failed | incomplete

改动文件：
  - src/app.py（新建）
  - Dockerfile（新建）
  - README/Web-a.md（新建）
  其他文件 mtime 未变。

难度基线 vs 实际交付：
  服务拓扑：原 nginx+php-fpm → 现 nginx+php-fpm（装进同一镜像，未替换）
  运行时：PHP 5.6（与原题一致）
  simplified: 无

手册：事实部分齐全；判断部分来源=官方题解 README.md（已搬运）；TODO=0
验证：<命令>，结果 == 结果: passed，阶段 handbook/.../solve
遗留：<缺材料、需人工、拿不准的地方；没有就写"无">
```

**改动文件清单是重点。** 有了它，主 Agent 的对账成本从"重读整个目录"降到"核对几个文件"。自己声明改了哪些文件、其余没动，才能证明没有越界。

## 5 规范文件与进度文件

### 共享规范文件放哪儿

批次大了以后，每个子 Agent 的任务书都塞满规则会吃光上下文。做法是写一份共享规范，所有子 Agent 读同一份。

**位置：交付根之外，和交付根同级。** 例如：

```text
<工作目录>/
├── _pack_spec/            ← 共享规范 + 进度文件，不在交付根里
│   ├── CONVENTIONS.md
│   └── STATUS.md
├── 容器题/
└── 附件题/
```

不要放进交付根：`verify.sh` 把 `_*` 前缀判成内部工作文件，直接 `failed`。也不要放进单个题目录，白名单不允许。

### 进度文件

建立一个交付状态文件，放在**交付根之外**（例如 `_pack_spec/STATUS.md`），每做完一道题更新一次：

```markdown
| 交付目录 | 形态 | provenance.status | verify | 手册 TODO | 备注 |
|---|---|---|---|---|---|
| Web-a | 容器题 | original_adapter | passed | 0 | |
| Web-b | 容器题 | independent_completion | partial | 2 | 缺原数据库快照 |
```

进度文件放在交付根之外，是因为它属于内部工作文件，交付目录白名单不允许出现（`verify.sh` 会把 `_*` 判成不该出现的文件）。

**状态从文件读，不要从聊天记录里回忆。** 上下文被压缩或换会话之后，只有落盘的状态是可信的。

## 6 主 Agent 做什么

主 Agent 的职责是对账和收尾，不是替子 Agent 干活，也不是盯着它们。

- **不要轮询。** 每轮只汇报"指标没变"会把上下文耗光，而任务一点没推进。子 Agent 有自己的上下文，它们不需要你照看。
- **保留至少一半上下文**用于最后的逐题对账：读产物、跑验证、核对手册和 provenance。
- **子 Agent 的结论要复核，不能直接采信。** 特别是"这题跑不通""这是环境限制""链路打不通"这类结论——要求它给出复现命令和证据，或者自己跑一遍。
- **不要把子 Agent 单方面的判断写进交付物。** `verify: environment_failed` 和"链打不通"必须由主 Agent 确认过再落盘，否则一道本来能解的题会被标成环境限制交出去。
- 子 Agent 报"上下文不够"时，把任务切小一格（一道题一个 Agent），不要让主线跟着停。

### 上下文快用完时

不要靠"开新会话"把问题丢给用户。按顺序做这三件事：

1. 停下新工作，把手上的题收尾到能落盘的状态。
2. 更新进度文件，把已完成、未完成、判断标准、材料位置写全。
3. 告诉用户当前状态和下一步，让用户决定怎么继续。

交接读文件，不要读聊天记录。把长篇聊天记录粘贴到新会话里，等于把上下文问题复制一遍。

### 接手检查清单

从别的 Agent 手里接一批题时，**先对账再动手**。不要相信任何一方的叙述，只看磁盘现状。

```text
[ ] 1. 读 `_pack_spec/STATUS.md`，确认哪些题标了 passed、哪些 incomplete、哪些没开始
[ ] 2. 对每道"已完成"的题跑一次 verify.sh，确认它现在的结论还是 passed
[ ] 3. 查文件 mtime：最近 15 分钟内有改动的目录，可能有另一路 Agent 在写
[ ] 4. 白名单扫一遍：ls -A 对照，看有没有半成品残留（_*.md、*.bak、临时脚本）
[ ] 5. 确认没有两个 Agent 同时写同一目录，有就先停一边
[ ] 6. 把对账结论写回 STATUS.md，再开始做没完成的题
```

**接手任务书里禁止写"前一个 agent 已经死掉了"。** 写这句话之后，一旦原 Agent 还活着，这个目录就有两个写入者了。

### 子 Agent 叫不醒时

真实情况里会遇到：`send_message` 返回 accepted 但子 Agent 不执行、`Team member limit 8 reached`、模型限流导致全部子 Agent 卡死。

按这个顺序降级，不要一直重试：

1. **确认是不是模型限流**。看子 Agent 最后一条消息的时间，如果全体同时停在同一时刻，多半是限流。换模型或等几分钟。
2. **换新 Agent 接手空目录**。旧 Agent 没有任何产出的目录，直接用新任务书从零开始，别试图唤醒旧的。
3. **自己做**。一批不超过 5 道时，主 Agent 自己做比协调子 Agent 快。
4. **做不完就停**。写进 STATUS.md，把已完成、未完成、判断标准、材料位置写全，告诉用户。**不要假装做完了。**

`9ea8c0d7` 那场 56 道题、8 个子 Agent 全部卡死，主 Agent 一个人硬撑到最后被用户叫停。正确做法是第 2 步就换策略，而不是反复 `interrupt_agent` + `spawn_teammate`。

## 7 只读审计也要隔离

"只读检查"不只是不改交付文件。**临时解包、import 脚本、跑工具都会在目录里留东西。**

真实事故：

- 审计员用 `tar -xOf ... | tar -xzvf -` 少写了 `-C`，把镜像是层解到了题目根目录，凭空多出一个 `flag`。用户要求「给出证据证明未被修改」。
- 审计员用 `python3 import` 核对 payload，在 `solve/` 下生成 `__pycache__/`。
- 审计员用 `cat >` 写临时脚本，忘了删。

规则：

1. **解包一律解到独立临时目录**：`T=$(mktemp -d) && tar -xf x.tar -C "$T"`。不要在题目目录里 `tar -x`。
2. **import 一律加 `-B`**：`python3 -B`，或 `PYTHONDONTWRITEBYTECODE=1`。
3. **临时脚本写到 `$(mktemp -d)`**，不要写在题目目录。
4. **要动源目录时先只读挂载或 `chmod -R a-w`**，跑完恢复。
5. **报告里如实说明越界**：如果留了东西，写清是什么、是否已清理、怎么核对。不要隐瞒。

用户对这件事的态度很硬：**「这个文件夹是绝对没有被修改过的，我才会阅读你的报告，我不能接受被篡改的情况，请给出证据证明未被修改。」** 被问到时要能给出完整证据链（mtime、目录条目变化、哈希抽查），不能只说"我没改"。

### 静态审计的结论要运行期复核

静态读代码得出的 S1/S2 级结论，**必须有运行期证据才能报**。真实误报：审计员只读了 INSERT 语句没读文件尾部的 UPDATE，判"默认口令可登录"是阻断级问题；另一个判 `@RequiresRoles` 不生效，运行期实测返回 510 无权限。

规则：S1/S2 没附运行期命令和输出，只能记「待确认」，不能写进阻断项。让用户为误报做决策，成本比漏报还高。

## 8 共用机器和共用目录

用远程 amd64 机器时：

- **远程 `/tmp` 和 Home 是多个人共用的。** 传包名带随机后缀（`/tmp/pk-<题目>-<随机>.tgz`），解压目录单独开一层父目录（`~/pack-<随机>/<交付目录名>`），解压后核对 md5。
- 用同名 tar 或同名解压目录，验证实际构建的可能是别人的镜像，结果不可信。
- 远程解压目录的 `basename` 必须等于交付目录名，否则 `verify.sh` 的手册文件名检查会失败。
- 跑完清掉自己的容器、镜像和临时目录。留着占资源，也干扰别人的验证。

本地工作区同理：**同一份题目只保留一处**。迁移或重组时先把新位置写全再删旧位置，不要留"两处各一份"。

## 9 收尾

一批做完，主 Agent 自己跑一遍 [SKILL.md](../SKILL.md) 的「交付前自检清单」，15 条逐条给结论。**不要等用户说"再检查一次"才检查。**

子 Agent 报 `passed` 只代表它那一格做完了；整批能不能交付，以主 Agent 对账后的结论为准。
