# 题目手册写法

手册写在 `README/<题目类型-题目名称>.md`，文件名和交付目录同名，一个字都不能少、不能改。截图放同目录的 `assets/`，正文用相对路径引用：`![截图](assets/image-20261007112926.png)`。

## 判断部分优先搬运

手册的九节分两类，分界线是**这句话能不能被验证**：

| 节 | 内容来源 | 为什么 |
|---|---|---|
| 1.1 题目名称 | 查证 | 和目录名、`challenge.yaml` 对得上 |
| 1.3 题目难度 | 查证 | 材料里通常标了 |
| 1.5 旗帜信息 | 查证 | 路径、权限、读取时机、覆盖命令全能查证 |
| 1.6 题目情况 | 查证 | 端口、账号、后台地址、check 位置全能查证 |
| 1.7 部署方式 | 查证 | 就是几条命令，构建跑一遍就知道对不对 |
| 1.2 题目描述 | **搬运优先** | 需要出题人的语气和意图 |
| 1.4 考察信息 | **搬运优先** | 需要真读懂题目 |
| 1.8 题目设计 | **搬运优先** | 需要理解设计动机 |
| 1.9 解题步骤 | **搬运优先** | 需要真打通链路 |

判断部分按下面的顺序找来源：

### 第一档：出题人材料——直接搬运

赛事归档、出题人交付包、旧题目录里带的详细设计文档、官方题解、题目源码里的设计注释，都算。搬进来整理成手册的语气，不留 TODO。

搬之前先确认那段文字确实来自原材料。**别把自己上一轮写的短手册当原材料搬**，也别把上一轮编的句子再搬一遍。

`last/` 目录就是放这些原始文档的地方（官方题解、出题人设计文档）。放了就不要改名，方便下一环核对搬运是否忠实。

### 第二档：外部 writeup / 战队 WP——只能当线索

战队解题报告、公开 writeup、博客文章，都不是出题人材料。它们和本题的交付环境**经常对不上**：注入点写错、参数形态写错、触发顺序写反、工具装法过时。

这一档的规矩是：**写进手册之前，必须在本次交付的环境里复跑核对。** 以实测为准改手册，不要以 writeup 为准改题。

核对不通过的部分不要搬。最常对不上的是：注入点在哪个参数、payload 的具体形态、多步触发的先后顺序、工具的安装方式。

**搬运和编造之间还有这一档，别把二手记录当出题人原话。**

### 第三档：确实没有来源——留 TODO

在该节正文写一行 `TODO(人工填写)`，并在交付说明里点名哪几节空着。不要写进 `<!-- -->` 注释，渲染出来看不见，空着的节没人发现。

**不许编。** 编出来的东西比空着更糟：「考察 Web 请求分析、服务端输入处理」这类句子读起来像内容，实际什么也没说，还会把空位掩盖掉，让人以为手册写完了。这类占位句、把问题退回来的句子（"具体漏洞点以 `src/` 中的原始实现为准"）、以及为了凑字数写的过程说明（"复现完成判据"）都算编造，一律不要写。

**有 TODO 残留时不要报"已完成"。** `verify.sh` 遇到 TODO 会判 `partial`。这个 `partial` 是正常结论，如实报告就行，不要为了跑到 `passed` 去编内容。

编号和层级照抄，顺序不能变。纯附件题去掉 1.7 部署方式，编号顺延（原 1.8 变 1.7，1.9 变 1.8）。`verify.sh` 两种骨架都认：容器题按九节查，附件题少一个 1.9 也算齐全。

## 写指引放注释里

写作过程中，每节末尾可以放一段 HTML 注释，写清这节要写什么、给个例子，交付前删掉。

```markdown
### 1.4 考察信息

TODO(人工填写)

<!--
真正考察的知识点，一行一个或顿号连起来。
必须和 1.8 的实际链路对得上，不要写大于实际考察面的范围。

例：Nginx location 匹配优先级、PHP-FPM 路径截断、文件上传 TOCTOU 竞态
-->
```

交付前把所有 `<!-- -->` 注释块删掉。

## 事实部分怎么写

### 1.1 题目名称

题目在平台上显示的完整名称，和交付目录、`challenge.yaml` 的 `name` 保持一致。

### 1.3 题目难度

五个档位选一个：简单 / 简单到中等 / 中等 / 中高难度 / 困难。材料里标了就照抄（赛事目录常按简单/中等/困难归类），没标就按 1.8 的实际链路估。

### 1.5 旗帜信息

**格式是「字段：值」平铺，一行一个字段，不用项目符号、不套代码块。**

```markdown
### 1.5 旗帜信息

原始静态flag：flag{opposeai_webassembly_jit_internal_validation}

平台覆盖方式：echo "$new_flag" > /flag

flag文件位置：/flag中，平台支持动态flag分发
```

按题目实际情况增减字段，常用的几个：

```markdown
### 1.5 旗帜信息

原始静态flag：材料里自带的那个占位值，照抄

平台覆盖方式：平台实际执行的写入命令

flag文件位置：容器内绝对路径，并说明程序怎么读它

权限属主：444 root:root（有特殊要求时才写）

读取时机：每次请求读 / 启动时读进内存 / 从数据库读
```

- **谁在什么时候读它这一条最容易出坑，必须写。** 每次请求读文件的题，平台换 Flag 立即生效；启动时读进内存的题（Python 模块级变量、Java `static` 块），平台换了 Flag 也不生效，得重启或重新触发链路。
- 程序读的不是 `flag.path` 时（软链接、包装文件、配置载入、数据库），把接法写清楚，并说明为什么必须这样接。
- 数据库或配置文件读 Flag 的题，把平台要执行的完整命令写进"平台覆盖方式"：

  ```markdown
  平台覆盖方式：docker exec <容器> mysql -uroot -proot -e "USE ctf; UPDATE flag_tab SET flag='$new_flag' WHERE id=1;"
  ```

- 旧平台用环境变量传值时，把变量名和处理位置写上。
- RDG 题没有 Flag 合同时，写明"这道题的敏感目标是配置里的固定内容，不从 `/flag` 读"，别让运维以为平台写 Flag 没生效。

### 1.6 题目情况

写"这道题跑起来是什么样"：监听哪些端口、有哪些服务、初始账号密码、后台地址、判题脚本在哪、有没有 ttyd、有没有依赖的数据库或外部服务。一行一件事。

```markdown
### 1.6 题目情况

容器同时运行 Apache、PHP 5.6、MariaDB 和 ttyd。

Web 端口：80
ttyd 端口：8022，账号 ctf/123456
后台地址：/admin506/，初始账号 admin/admin
数据库：容器内 MariaDB，首次启动导入 src/docker/init_zzzcms.sql
正式判题脚本：check/check.sh
```

RDG 题的 ttyd 端口和账号必须有，选手要靠它进容器改代码。

### 1.7 部署方式

八项清单，逐项写全。命令要能直接复制执行。

**这一节最容易漏三样：`--name`、`docker load -i`、清理命令。** 下面给一份完整模板，照填空题一样替换值就行。

````markdown
### 1.7 部署方式

`src/` 是题目源码和静态资源；`solve/` 是本地验证脚本，不进镜像；`镜像/` 是导出的镜像 tar；`附件/` 是发给选手的文件。

在本目录构建：

```bash
docker buildx build --platform linux/amd64 -t afterimage:latest --load .
```

交付了镜像 tar 时改用（tar 路径和 1.5 的镜像名一致）：

```bash
docker load -i 镜像/afterimage.tar
```

启动容器。`/start.sh` 是平台入口，末尾必须显式带上；`--name` 必须和后面清理命令里的名字一致：

```bash
docker run -d --name afterimage \
  -p 8080:80 \
  afterimage:latest /start.sh
```

访问地址：

Web：http://127.0.0.1:8080/
后台上传入口：http://127.0.0.1:8080/admin/upload.php

平台启动后写入 Flag（平台实际用的是后台配置的 `flag_script`，这里给等价的本地模拟命令）：

```bash
docker exec afterimage sh -c 'printf "%s\n" "$1" > "$2"' sh 'flag{example}' /flag
```

停止并清理：

```bash
docker rm -f afterimage
```

端口按现场环境调整时，以下四处要同步改：`Dockerfile` 的 `EXPOSE`、`challenge.yaml` 的 `expose_ports`、本手册 1.6 和 1.7 的端口、`solve/solve.py` 的默认 `PORT`。
````

旧平台用 `changeflag.sh` 的题，把 `-e FLAG='...'` 的启动方式也写进来。

### Web / AI 类题的入口页

**选手打开的第一屏必须是能说明这道题是什么的页面。** 不能是 `NOT-FOUND` 纯文本、不能是空白 `index.html`、不能是 `{"error": "not found"}`。

- 官方有页面就用官方的截图/原页面。
- 官方没有就照题目场景做一个：业务系统的登录页、客服对话窗口、文件上传台、监控面板。
- 同一批题目**不要用同一个模板套**。做完一道看一眼，和上一道长得一样就重做。

用户对这件事的原话是「每个题目的页面最好是官方的那个，最差也要自己好好的整哈，不能糊弄我哈」「每个题目的样式不能都几把一模一样」。

### 1.5 里的 flag_script

动态 Flag 题的手册 1.5 要贴出**可以直接复制到平台后台的 `flag_script` 原文**，出题人不用自己写：

````markdown
### 1.5 旗帜信息

原始静态flag：flag{placeholder}

平台覆盖方式：在平台后台题目配置的 flag_script 里填下面这段

```bash
#!/bin/bash
set -uo pipefail
printf '%s\n' "$new_flag" > /flag
chmod 444 /flag
```

flag文件位置：/flag

读取时机：每次请求读
````

`$new_flag` 必须保留，平台会把它替换成本实例的动态值。模板说明见 [platform.md](platform.md)。

## 附件题的差异

去掉 1.7 部署方式，编号顺延（原 1.8 变 1.7，1.9 变 1.8）。另外：

- 1.6 题目情况写清发了哪些附件、每个附件是什么、选手需要什么环境打开。
- 解题步骤末尾写清解到的是什么、是否需要联网。

`verify.sh` 对附件题的手册检查接受这两种骨架：八节顺延，或者写满九节。**不要**为了凑九节硬加一个空的 1.7 部署方式。

附件题的 1.5、1.6 按上面的差异写，`verify.sh` 不会拿容器题的字段（端口、账号、地址）去卡它：1.5 只要在本节写了 Flag 这件事（静态 Flag 写「平台覆盖方式：无」、RDG 无 Flag 合同写清敏感目标不是 `/flag`）就算写了，1.6 要求本节有内容。

## RDG 题的差异

骨架同上，另外：

- 1.5 说明这道题的 Flag 是动态写入还是固定值设计的一部分。
- 1.6 列出 ttyd 端口和账号、后台地址和账号、`check/check.sh` 的位置。
- 1.8 可以先列出 check 覆盖了哪几个关卡（从 `check.py` 里读出来），但**每个关卡为什么这么判定、加固前后分别是什么结果**要人工补。
- 1.9 改成"初始漏洞验证 + 修复方法 + 加固后自检"三段。

## 交付前必做

1. 删掉所有 `<!-- -->` 注释块和写指引。交付后 `grep -c '<!--' README/<题目名>.md` 应该是 0。
2. 确认没留下编造的内容。`grep -c 'TODO(人工填写)' README/<题目名>.md` 不是 0 说明还有空位，不要用"章节齐全"糊过去，在交付说明里如实写出哪几节还空着。
3. **手册文件名必须和交付目录逐字一致**：`README/<题目类型-题目名称>.md`。写成 `题目手册.md`、`joomla-char-escape.md`（英文小写连字符）、`README.md` 都会被判失败。
4. **正文和实测对得上**。1.9 的每条命令、每个 payload 形态、每个触发顺序，用本次交付目录里的 `solve/solve.py` 复跑一遍。对不上的改手册。
5. **手册里提到的路径都存在**。逐个 `test -e`：`src/...`、`附件/...`、跨题目录的引用。写"源码见 `src/client/main.go`"而那个目录不存在，是常见的漏项。
6. 附件题的 1.6 里声明的附件文件名集合，和 `附件/` 里的实际内容做差集，差集必须是空的。
7. 不写"常见失败现象"这一节，排障记录不属于交付手册。
8. 不用 emoji，不堆加粗，不写"本题目旨在……"这类铺垫。
